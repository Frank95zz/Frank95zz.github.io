# 推理效率：已经测到了什么，还不能证明什么

2026-11-06。**缓存后的命令生成环节更省时间；当前证据尚不能证明完整视频到机器人流程比 RGB 更快，也不支持端到端实时主张。** 训练耗时、预处理耗时、部署推理延迟和录像生成时间必须分开报告。

本轮未启动新 GPU 工作、未修改 R38 训练代码或配置、未停止任何进程。现有 GPU0/2/3/4/5 在运行 R38，GPU1 属于其他任务。新微基准使用单 CPU 线程、`nice 10`、禁用 CUDA。整机为 6×NVIDIA A40、双路 AMD EPYC 7542；同机任务仍有 CPU/内存竞争，结果不是隔离硬件最优性能。

## 1. 先统一计时口径

`RTF = 处理墙钟秒 / 输入视频秒`，越低越好。RTF<1 只说明平均处理快于视频时间；它不能证明输入是因果的，也不能保证每个控制周期都不超时。

|成本|本项目实际内容|应否计入新视频端到端延迟|
|---|---|---|
|离线训练|配对数据制作、teacher/retarget 标签、网络训练与选模|单独报告摊销成本，不计入每次部署推理|
|GVHMR前端|重采样、人物跟踪、ViTPose、HMR2特征、GV全视频恢复|必须；缓存实验不能省略后仍称端到端|
|145D→命令|时间采样、Motion Transformer、共享命令头、motion残差、FSQ|必须；每个anchor一次输出5个20ms命令|
|SONIC低层控制|token64＋实际proprio930→29D action|每20ms控制周期均执行|
|PD与物理|每命令4个5ms PD/MuJoCo步|仿真回放计入；实机应另测传感/通信/执行deadline|
|可视化|mesh、三栏合成、MP4编码|科研交付成本单列；控制器运行不需要生成MP4|

实际 GV-only 真人输入不运行 VideoMAE。然而当前通用预测程序仍初始化原 RGB provider；所以历史任务墙钟含无用的视觉初始化及数据核验。下面另外抽取**原训练checkpoint的等价运动子模块**测量驻留推理，无须改动生产源码。

## 3. 本轮新增CPU实测：训练checkpoint、真实输入、逐次计时

来源：[CPU微基准原始结果](../../outputs/research39_efficiency/cpu_benchmark.json)。固定 R37 GV-only@12000，SHA256 `527a27ea3f20bd813483f7bc848fa1fb0387282f20ff352773088b705176ea88`。PyTorch/ONNX均单线程，batch=1，已加载模型；计时使用 `perf_counter`。motion每源预热10次，decoder预热20次；首次命令单独留存，不混入预热后的分位数。所有逐次耗时、重复序号和源码hash均保存，执行时源码另存为`outputs/research39_efficiency/benchmark_cpu_measured_snapshot.py`。

|测量阶段|样本和重复|均值ms|P50ms|P95ms|计时单位与边界|
|---|---|---:|---:|---:|---|
|缓存145D→命令，含插值、Transformer、共享head、motion残差和FSQ|12源×3次，2514个anchor|1.450|1.423|1.589|**一个anchor输出5条命令**，覆盖100ms；不是一条命令的延迟|
|SONIC CPU decoder|S57 walking 375帧×3次=1125|8.750|8.668|9.137|一条token＋930D实际状态→29D action；不含物理|
|4×PD/MuJoCo advance|同一真实走路轨迹，1125次|1.691|1.659|1.965|一个20ms控制周期内的4个5ms物理步；不含decoder|
|SONIC＋状态/接触记录＋4×PD/MuJoCo完整step|同一真实走路轨迹，1125次|10.933|10.829|11.542|一个20ms控制周期；内含上一行，不可重复相加|

缓存命令阶段3遍合计RTF=0.01460；完整CPU step三遍耗时4.108/4.127/4.067秒，各回放7.5秒，RTF=0.54677。三遍重新初始化的物理轨迹与历史保存的 `full_qpos` **最大差为0**，并非用随机输入替代仿真。抽取运动子模块输出与原GPU预测的pre-FSQ最大绝对差仅 `6.85×10⁻⁷`，确认测的是实际训练模型的等价路径。

模型驻留后，每源首次命令生成均值2.067ms，P50=1.918ms、P95=3.023ms；这12次并非12次冷进程启动。运动模块加载0.047秒，SONIC ONNX初始化0.398秒，这些只有一次观测；不是可复用的冷启动P95。完整step最大27.136ms，1125次中有2次超过20ms。因此目前可以说“该样本下CPU低层回放平均快于50Hz时间预算”，**不能说硬实时得到保证**。R38额外heading/gain反馈尚未包含在此微基准，需另列开销。

## 4. 为什么仍然不是实时系统

当前 GVHMR 恢复读取完整视频；Motion encoder每个anchor读取[-1.0,+0.5]秒16个时间点。计算1.45ms不能消除全视频可用等待及未来信息依赖。RGB路线也有+0.5秒窗口，但两种前端信息延迟并不相等。

因此必须区分：①已录制视频准备好到首条命令的计算延迟；②视频采集到动作执行的因果延迟；③模型驻留后的单步耗时。现有收据未记录真正首条结果到达时间，不能倒推；本轮CPU的首条数字明确从“GV特征与权重已就绪”开始计时。

当前缓存由`--static_cam`生成，只验证固定相机条件。GV坐标利用重力与视向，人体模型是SMPL-X；估计尺度、朝向和平移仍可能有误差。移动相机需要官方VO路径并独立计时/评估，不能将固定相机成本冒充通用视频成本。使用的是SIGGRAPH2024 checkpoint及六点静止概率，不是已验证TPAMI新增独立SLP。

## 5. 已准备的公平端到端补充实验

独立脚本已保存到 `scripts/research39_efficiency/`，没有修改原训练绑定。独立manifest为[36项配对基准](../../outputs/research39_efficiency/gpu_protocol/manifest.json)：相同12DEV×3遍，按重复序号交替GV/RGB运行顺序，整批顺序执行以避免多视频并发污染；每次GV新建输出，实际重新提取。保留相同83.52秒共同可用命令区间、原始视频分辨率、checkpoint、初始状态与控制器。

每次记录GV预处理/估计、145D导出、命令模型加载、第一条/全部命令、CPU仿真、总RTF、设备与缓存边界。RGB走原生产预测入口，GV走已校验等价的精简模块，因此最终首先报告**部署实现效率**；若要作纯架构速度主张，还需统一两路常驻服务初始化边界。正式RGB的首条命令事件尚未插桩，脚本将其记null，绝不把整条文件完成时间伪装为第一条延迟。视频渲染单列，不混入动作推理。

准备脚本、CLI、源码绑定及独立runtime preflight已通过无GPU校验；**CPU实测已完成；同源完整GPU基准已安排在R38结束后自动执行，目前尚无GPU基准结果，不能预填**。后台等待器PID **27637**，以`start_new_session`脱离终端，等待阶段不预约GPU；状态与恢复入口写入`outputs/research39_efficiency/gpu_protocol/waiter_launch.json`。安全入口默认仅查状态，不预约卡：
